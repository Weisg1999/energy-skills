# 江苏工商业储能 · 电费优化样板实例

> 本目录是 `skills/tariff-bill-optimization/instances/` 的第一个纵向切片：**一省（江苏）+ 一主体（10 kV 工商业用户 + 用户侧储能）+ 一套账单口径（两部制 + 分时 + 力率）**。配置改 `instance.json`，负荷换 `data/load_demo.csv`，运行 `run.py`，不改代码。
>
> 所有演示数据为 **D 级合成数据**，不代表任何真实用户、电费单、合同或储能收益。省级电价参数必须以江苏省现行文件整表替换后再谈结论。

## 1. 一条命令

```bash
# 配置校验 + 来源分级
python skills/tariff-bill-optimization/instances/jiangsu-ci-storage-2026-11/run.py --check-config

# 合成数据全流程：逐月账单 → 基本电费三方式 → 削峰降需量 → 复核表
python skills/tariff-bill-optimization/instances/jiangsu-ci-storage-2026-11/run.py --demo

# 真实负荷（12 个月 × 96 点，路径指向仓库外）
python skills/tariff-bill-optimization/instances/jiangsu-ci-storage-2026-11/run.py \
  --load /path/to/load_2026.csv --out /path/to/out
```

合成负荷可重新生成：

```bash
python skills/tariff-bill-optimization/instances/jiangsu-ci-storage-2026-11/make_demo.py
```

## 3. 运行逻辑

1. **配置校验**：六个块齐全；时段表覆盖 0–24 时且不重叠；每个时段有价格；基本电费参数、40% 下限、105% 超需倍数、力率档位齐全；合同需量不低于下限且不超过变压器容量；负荷契约要求 12 个月 × 96 点。
2. **读负荷**：逐行校验月份 1–12、slot 0–95、无重复无缺口、负荷非负。真实数据放仓库外，用 `--load` 指向。
3. **逐月账单**：电能量按 `tariff.tou_energy_cost` 汇总到四个时段，乘当月天数；输配、系统运行、基金按全电量；基本电费按所选方式（容量 / 合同需量 / 实际需量）计算；力率调整按简化两段口径作用于电能量侧小计（`bill.bill_breakdown`）。
4. **基本电费三方式**：逐月比较按容量、按合同需量（最优申报）、按实际需量，输出当月最便宜的方式；不允许全年一个方式一刀切。
5. **申报优化**：按 `D* = max(40% 下限, A/1.05)` 计算理论最优申报值，其中 `A` 是该月实际最大需量；这是**事后理论上界**，不是可执行的事前策略。
6. **削峰降需量**：以当月最大需量的 88% 为目标线，在峰/尖段按恒功率块放电，在谷段有裕度时充电；放电量受功率、可用能量与日循环上限约束，充电量按 RTE 折算。削峰后重新计算最大需量与最优申报。
7. **收益拆分**：`申报优化节省 = 当前账单 − 仅重算申报`；`储能净节省 = 仅重算申报 − (储能后账单 + 退化 + 运维)`；两者分开列示，不把申报优化算成储能收益。
8. **复核表**：把账单结构、三方式、削峰口径、回收期和未核实项写在一页，便于逐项替换真实参数。

## 4. 合成演示的基准输出

基准用户：1,600 kVA 变压器、当前合同需量 1,000 kW、功率因数 0.92；储能 500 kW / 1,000 kWh、可用比例 95%、RTE 90%、退化 0.05 元/kWh、资本开支 900 元/kWh；策略为按月度最大需量削峰 12%、谷充峰放、日循环 1 次。

| 项目 | 金额（万元/年） |
|---|---:|
| 当前账单（合同需量 1,000 kW） | 663.91 |
| 仅重算申报、不加储能 | 658.68 |
| 储能削峰 + 重算申报 | 647.47 |
| 申报优化节省（vs 当前） | 5.23 |
| 储能净节省（vs 仅重算申报） | 7.01 |
| 合计节省（vs 当前） | 12.23 |

- 储能放电 113.9 MWh、充电 126.6 MWh，平均削峰 54.7 kW；退化与运维合计 4.20 万元/年。
- 储能资本开支 90.0 万元，仅按储能净节省计算的静态回收期 **12.84 年**。
- 最大需量从 1 月的 943 kW 升到 8 月的 1,311 kW；当前 1,000 kW 合同在 4–10 月触发 105% 超需加价，这是申报优化空间的主要来源。

**读数**：回收期偏长不是模型错误，而是策略选择的结果——12% 的削峰目标只用到储能容量的一小部分，大部分时段电池闲置。把 `shave_ratio` 调大、或把放电集中到尖段，会改变储能节省与回收期；这类比较应复制 `instance.json` 改 `profile_id`，保留旧输出。`900 元/kWh` 与 `0.05 元/kWh` 退化均为 D 级占位，真实项目必须替换。

| 申报下限 | 变压器容量的 40% | D | 合成简化；江苏含高压电机时基数可能不同 |

| 江苏现货状态 | 2025-08-29 起连续结算试运行 | B/C | 仅作背景；现货价格不进入本包电费计算 |

未核实的省级电价不会被估算成"江苏价格"：`rules.tariff.status`、`rules.basic_charge.source` 与复核表均明确标注 D 级合成，`--check-config` 会打印"落地必须整表替换"。

## 6. 风格档与指纹

当前风格 `jiangsu-ci-storage-balanced-v1`：削峰 12%、谷充峰/尖放、日循环上限 1 次、最小价差 0.30 元/kWh、合同需量按月按 `A/1.05` 重算。

`policy` 块规范化 JSON 的 SHA-1 前 12 位作为**风格指纹**写入复核表（当前 `4a210e513c99`）。比较两个方案时先看指纹：指纹不同，差异首先归因于策略；指纹相同，才归因于负荷、电价或设备。

## 7. 依赖与边界

- **依赖**：仅 Python 标准库；计算内核来自 `skills/tariff-bill-optimization/tools/`（`bill.py`、`demand.py`、`tariff.py`、`curves.py`），不修改内核。
- **纳入**：电能量、输配、系统运行、基金、基本电费三方式、简化力率、储能削峰降需量、退化与固定运维、月度申报重算。
- **未纳入**：零售套餐比价（用 `tools/retail.py` 单独跑）、代理购电分摊、双路进线与高可靠性供电费、需量预测误差、SOC 逐点与备用约束、电池寿命衰减曲线、税费与融资。
- **不是**：不是电费单复核的替代品，不是储能投资建议；`A/1.05` 申报是事后上界，实际申报必须用负荷预测。
- 真实负荷放仓库外，用 `--load/--out` 指向本地路径；仓库内只保留 D 级合成样例。
